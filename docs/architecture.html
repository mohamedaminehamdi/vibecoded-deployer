Architecture

What gets created, how a run decides what to do, and the design choices you inherit.

Overview#

Everything runs in your own GitHub repository and AWS account. The deploy workflow provisions infrastructure with Terraform, builds your Lovable repository, uploads the build and creates the DNS record. At request time only DNS, CloudFront, ACM and S3 are involved; GitHub Actions is not in the request path.

The workflow also creates the DNS CNAME with the AWS CLI (Route 53) or the GoDaddy API. That record is not managed by Terraform.

How a run decides what to do#

The first step of the deploy workflow checks whether the bucket <subdomain>.<domain_name> exists, and if so looks for a CloudFront distribution that has an origin whose domain name contains the bucket name.

The build and upload steps always run. In order, a full run does this:

  1. Looks up the Route 53 hosted zone ID (Route 53 only; the run fails if no zone is found).
  2. Writes terraform/backend.tf for the project's state key, then terraform init -reconfigure.
  3. Runs terraform refresh (failures ignored) and terraform apply -auto-approve (failures do not fail the job; 20 minute timeout).
  4. Prints the key Terraform outputs, and the certificate validation records when the certificate needs manual validation. Both only happen when the apply succeeded.
  5. Re-applies the bucket's public access block, website configuration and bucket policy with the AWS CLI (failures ignored).
  6. Checks out your Lovable repo, runs npm ci and npm run build and picks the first of out, build, dist that exists.
  7. Runs aws s3 sync --delete and creates a CloudFront invalidation for /* (failure ignored).
  8. Reads the CloudFront domain from Terraform (falling back to the bucket's S3 website endpoint if that is empty) and writes the CNAME at your DNS provider.

A redeploy skips steps 1 to 5 and 8, and takes the distribution ID from the first check.

Check the logs

Because the Terraform apply step is continue-on-error and the final summary text is fixed, a green run does not prove that every resource was created. If Verify Infrastructure was skipped, the apply failed.

Terraform state#

  • Where: s3://<state bucket>/projects/<repo_name>/terraform.tfstate, in us-west-2, encrypted. The state bucket is the one you created with terraform/bootstrap; its name comes from the TERRAFORM_STATE_BUCKET secret or defaults to lovable-deployer-terraform-state.
  • Locking: S3 native lock file (use_lockfile = true), no DynamoDB.
  • Backend config: generated by the workflows on every run and never committed (terraform/backend.tf is git-ignored).
  • Isolation: one state per repo_name.

One deployment per repo_name

The state key does not include the domain or subdomain. Deploying the same repo_name to a second subdomain would make Terraform compare the new variables against the first deployment's state and plan changes to those resources. Treat repo_name as the identity of a deployment.

Design choices to be aware of#

  • Public bucket, HTTP origin. CloudFront fetches from the S3 website endpoint over HTTP, so the bucket must be publicly readable. Anyone who knows the bucket's website endpoint can read the files without CloudFront. There is no origin access control.
  • Single-page-app routing. Missing paths return index.html with status 200, both from S3's error document and from CloudFront's custom error responses for 403 and 404. Deep links work, but real 404s are never reported.
  • Caching. CloudFront's default TTL is one hour (minimum 0, maximum 24 hours). The workflow invalidates /* after every deployment so changes appear quickly.
  • Certificate region. CloudFront only accepts certificates from us-east-1, so Terraform uses a second AWS provider alias for ACM.
  • Provider and region choices are hard-coded. See the fixed values.
