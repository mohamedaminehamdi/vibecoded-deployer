Troubleshooting, FAQ and limitations

Symptoms, causes and fixes, followed by the questions people ask most and the limits you should know about.

Open the failing run in the Actions tab and expand the step that is red (or the one that should have run). Several steps are continue-on-error, so a green job can still hide a failed step.

Troubleshooting#

Before and during Terraform#

Could not find Route 53 hosted zone for <domain>

The workflow found no hosted zone named exactly domain_name in the AWS account behind your keys. Create the zone, or check for a typo, an extra subdomain label in domain_name, or credentials from a different account. If your DNS is at GoDaddy, use dns_provider = godaddy instead.

Terraform init fails: bucket does not exist or access denied

Check, in this order:

  • Did you run terraform/bootstrap?
  • Does the bucket name match the TERRAFORM_STATE_BUCKET secret, or the default lovable-deployer-terraform-state when the secret is not set?
  • Is the bucket in us-west-2? The workflows hard-code that region for the backend.
  • Can your IAM user list the bucket and read, write and delete objects in it (the lock file included)?
Error acquiring the state lock

A cancelled or crashed run can leave a lock file (terraform.tfstate.tflock) next to the state object. Make sure no other run is active, then run terraform force-unlock <LOCK_ID> with the project's backend configuration, or delete the lock object from the state bucket.

Unsupported argument "use_lockfile" (running Terraform locally)

S3 native locking needs Terraform 1.10 or newer. The workflows install the latest Terraform, so this only affects your own machine.

The job is green but the site does not load

The Terraform apply step is continue-on-error. Open its log. If Verify Infrastructure was skipped, the apply failed and no CloudFront distribution may exist. The final summary text is fixed and does not prove success.

With GoDaddy this is expected on the first run; see the GoDaddy flow.

Terraform apply times out after 20 minutes (Route 53)

With Route 53, Terraform waits for ACM to issue the certificate. That never happens if the hosted zone is not the one your domain's nameservers point to. Compare the zone's NS records with the nameservers set at your registrar, then run the workflow again.

BucketAlreadyExists

S3 bucket names are global. <subdomain>.<domain_name> is already used, probably in another AWS account. Choose a different subdomain.

AccessDenied when applying the bucket policy

The site bucket is public by design. If S3 Block Public Access is enabled at the AWS account level (or by an organization policy), attaching a public bucket policy is rejected. Adjust that setting for this account if a public static site is what you want.

Build and upload#

Repository not found when checking out the Lovable repo

The workflow checks out <owner of this repo>/<repo_name>. Check the spelling of repo_name and that the Lovable repo belongs to the same owner. If it is private, add an ACCESS_GITHUB_TOKEN secret with read access to that repository's contents.

npm ci fails

npm ci needs a committed package-lock.json that matches package.json. Run npm install locally and commit the updated lock file.

The build fails, but works on my machine

The workflow builds with Node.js 18. If a dependency needs a newer Node.js, change node-version in the Setup Node step of the deploy workflow.

Could not find build output directory

npm run build must produce out/, build/ or dist/ in the repository root; the first one found is used.

After a deployment#

I still see the old version

The invalidation step is continue-on-error; check that it ran. CloudFront's default TTL here is one hour and browsers cache too, so try a hard refresh or a private window.

The name does not resolve, or it resolves to the wrong place

Allow for propagation (TTL 600 seconds). Make sure the provider you selected is the one your nameservers point to; the CNAME is written there and nowhere else. Check with dig +short <subdomain>.<domain_name> CNAME. It should return a *.cloudfront.net name.

Browser shows a certificate warning

The name may still point at the S3 website endpoint (the fallback used when Terraform produced no CloudFront domain), which has no certificate. Fix the Terraform failure and run the workflow again; see the GoDaddy flow if you use GoDaddy.

Destroy#

The destroy job was skipped

confirm_destroy must be exactly DESTROY, in capitals.

Destroy fails because the bucket is not empty

The emptying step makes one delete-objects call, which AWS limits to 1000 keys, and ignores its failure. Empty the bucket yourself (for example with aws s3 rm s3://<bucket> --recursive), then run destroy again.

The summary says "No state found", but my DNS record disappeared

The DNS deletion steps do not depend on the state check. A mistyped repo_name with a correct domain and subdomain leaves AWS resources untouched but still deletes the CNAME. Re-create it by running the deploy workflow with force_infrastructure set to true, and re-run destroy with the right repo_name.

FAQ#

Does it only work with Lovable?

It is built for Lovable-generated React repositories, but the workflow only requires that npm ci and npm run build succeed and produce static files in out/, build/ or dist/.

Can I deploy to the apex domain or add a www redirect?

No. subdomain is required, and the certificate, bucket and CloudFront alias are all <subdomain>.<domain_name>.

Can I host several sites?

Yes. Run the workflow once per Lovable repo with its own repo_name and subdomain. All of them share one state bucket and keep separate state files.

Can I deploy one repo to staging and production?

Not safely. The state key contains only repo_name, so a second subdomain for the same repo would be planned against the first deployment's state. Use separate repositories (for example a fork per environment).

Can I use a private Lovable repo?

Yes, with an ACCESS_GITHUB_TOKEN secret that can read it. It must still belong to the same owner as your copy of this repository.

How do I change the region or the Node.js version?

Edit them in the code: us-west-2 appears in both workflows, terraform/main.tf and terraform/bootstrap/variables.tf; Node.js 18 is set in the deploy workflow. The certificate must stay in us-east-1. See the fixed values.

How do I roll out an updated version of this repository to an existing site?

Merge or pull the changes into your copy, then run the deploy workflow with force_infrastructure set to true. Terraform applies the difference against the existing state. Read the changelog first, and consider running terraform plan locally against the project's state.

What does it cost?

AWS charges for S3 storage and requests, CloudFront data transfer and requests, and Route 53 if you use it. ACM public certificates are free.

Limitations#

  • One deployment per repo_name. The state key has no domain or subdomain in it.
  • Subdomains only. No apex domain, no www redirect.
  • Same GitHub owner, default branch only. There is no branch or tag input.
  • Static output only, built with npm ci and npm run build on Node.js 18.
  • The bucket is public, and CloudFront reaches it over HTTP via the S3 website endpoint, without origin access control. Do not host private content.
  • Fixed regions: us-west-2, plus us-east-1 for the certificate.
  • Long-lived AWS keys. No GitHub OIDC support.
  • GoDaddy certificate validation is manual, so a first GoDaddy deployment takes two runs.
  • Failures can be quiet. Terraform apply and cache invalidation are continue-on-error, and the run summary text is fixed.
  • Very large sites. Teardown empties the bucket with one delete-objects call, which handles at most 1000 keys.
  • No automated end-to-end tests. CI checks Terraform formatting and validity and workflow syntax only.
