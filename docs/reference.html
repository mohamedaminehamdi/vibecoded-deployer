Every input, secret and hard-coded value, taken from the workflows and Terraform in the repository.

Deploy workflow inputs#

Workflow Deploy Lovable Website (.github/workflows/deploy-lovable-website.yml), trigger workflow_dispatch.

Deploy workflow inputs
InputTypeRequiredDefaultDescription
repo_namestringyesName of the Lovable repository, without the owner. Checked out from <owner of this repo>/<repo_name> at its default branch. Also names the Terraform state key projects/<repo_name>/terraform.tfstate.
domain_namestringyesRoot domain, for example example.com. For Route 53 it must exactly match the name of a hosted zone in your AWS account.
subdomainstringyesLabel to publish on. The site is served at <subdomain>.<domain_name>; the same string is the S3 bucket name and the certificate name. Apex domains are not supported.
dns_providerchoiceyesnonegodaddy or route53. The form lists godaddy first, so double-check your selection.
force_infrastructurebooleannofalseRun the Terraform and DNS steps even when the bucket and the CloudFront distribution already exist. Terraform applies whatever differs from its state; nothing is recreated unless Terraform decides to.

Destroy workflow inputs#

Workflow Destroy Lovable Website (.github/workflows/destroy-lovable-website.yml), trigger workflow_dispatch.

Destroy workflow inputs
InputTypeRequiredDescription
repo_namestringyesThe repo_name used at deploy time. Selects the Terraform state to destroy.
domain_namestringyesRoot domain, as used at deploy time.
subdomainstringyesSubdomain, as used at deploy time.
confirm_destroystringyesMust be exactly DESTROY (case sensitive). With any other value the job is skipped.

AWS permissions#

The IAM user behind AWS_ACCESS_KEY_ID must be able to do everything below. This repository does not ship a tested minimal IAM policy; build one from this list and try it with a throwaway domain before relying on it.

AWS calls made by the workflows
ServiceCalls made directly by the workflows
S3head-bucket, put-public-access-block, put-bucket-website, put-bucket-policy, sync (list, put, delete objects); on destroy list-object-versions, delete-objects and rm for the state file
CloudFrontlist-distributions, get-distribution, create-invalidation, wait distribution-deployed
ACM (us-east-1)delete-certificate (destroy)
Route 53list-hosted-zones-by-name, list-resource-record-sets, change-resource-record-sets

On top of that, Terraform (AWS provider 5.x) needs create, read, update and delete rights on the S3 bucket and its sub-resources, the ACM certificate and its validation, the CloudFront distribution, and the Route 53 validation records, plus read and write access to the state object and its lock file in the state bucket.

Credentials

The workflows use long-lived access keys. They do not support GitHub OIDC. Use a dedicated IAM user, scope it as tightly as you can and rotate the keys.
