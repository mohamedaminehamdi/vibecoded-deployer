Redeploy and teardown

Update a live site quickly, or remove it completely.

Redeploy after code changes#

  1. Push your changes

    Commit and push to the default branch of the Lovable repository. The workflow has no branch or tag input.

  2. Run Deploy Lovable Website with the same inputs

    Use the same repo_name, domain_name, subdomain and dns_provider.

If the S3 bucket <subdomain>.<domain_name> and a CloudFront distribution whose origin contains that bucket name both exist, the run is a redeploy. It skips Terraform and DNS, builds your app, runs aws s3 sync --delete and invalidates /*. If either one is missing, it runs the full flow instead.

When to use force_infrastructure#

Set it to true to run the Terraform and DNS steps even though the infrastructure exists, for example to repair drift or to re-write the CNAME. Terraform applies the difference between its state and the code; it does not delete and recreate anything on its own. It will fail if the resources exist but are not in the project's state.

Destroy a site#

Irreversible

The destroy workflow deletes the S3 bucket and everything in it, the CloudFront distribution, the certificate, the DNS record and the Terraform state. There is no undo.

  1. Open the workflow

    Actions, Destroy Lovable Website, Run workflow.

  2. Fill in the inputs

    repo_name, domain_name and subdomain exactly as used at deploy time, and DESTROY as confirm_destroy. Any other confirmation value makes the job skip.

What it does, in order#

The workflow looks for Terraform state under projects/<repo_name>/. When state exists it:

  1. Reads the bucket name, distribution ID and certificate ARN from the Terraform outputs.
  2. Empties the S3 bucket, including object versions and delete markers.
  3. Runs terraform destroy: bucket, certificate, distribution and Route 53 validation records.
  4. Waits for the distribution if it is still being disabled, and tries to delete the ACM certificate if it still exists (both best effort).
  5. Deletes the state file and its .backup from the state bucket.

Whether or not state exists, it also tries to delete the CNAME <subdomain>.<domain_name> in the Route 53 zone named domain_name (if found), and at GoDaddy if GODADDY_API_KEY is set. Both are best effort and both run regardless of the provider you deployed with.

Mistyped repo_name

If repo_name does not match any state, nothing in AWS is destroyed, but the DNS deletion steps still run for the domain and subdomain you entered, while the summary says no resources were removed. Double-check the inputs.

What is left behind#

  • Your Lovable repository and this control repository.
  • The state bucket created by terraform/bootstrap, shared by all projects. To remove it, empty it (including versions) and run terraform destroy -var="state_bucket_name=..." in terraform/bootstrap.
  • Any certificate validation CNAME you created by hand in GoDaddy.
  • Anything the best-effort steps could not remove. Check the run log for messages such as Certificate may already be deleted or still in use.
